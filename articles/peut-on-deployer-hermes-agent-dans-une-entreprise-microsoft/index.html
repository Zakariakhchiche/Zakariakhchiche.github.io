Peut-on déployer Hermes Agent dans une entreprise Microsoft ?

Intune, Teams, Entra ID, Graph : ce qui fonctionne déjà, ce qui manque encore, et la checklist que j’applique avant un pilote

Zakaria Khchiche · 16 octobre 2026 · également publié sur Medium

Réponse courte : oui pour un pilote encadré, pas encore pour un déploiement généralisé sans travail préalable. Depuis son arrivée sur le Microsoft Store, Hermes Agent (Nous Research, open source, licence MIT) peut être poussé par Intune comme n’importe quelle application du Store. Il parle déjà à Teams, à Microsoft Graph et à Microsoft Foundry via Entra ID. En revanche, la gouvernance (secrets, contrôle d’accès, journalisation) reste à construire par la DSI.

Je suis Tech Lead Data & IA et j’accompagne des grands comptes sur la mise en production d’agents (plus de 200 agents en production chez SUEZ). J’ai lu le code de Hermes Agent côté Microsoft, et j’y ai proposé deux correctifs, en revue chez les mainteneurs. Voici ce que j’en retiens pour une entreprise équipée Microsoft 365.

Ce qui change avec le Microsoft Store

Jusqu’ici, installer Hermes Agent sur Windows passait par un script PowerShell ou une commande dans un terminal. Aucune DSI ne valide ça pour 500 postes.

Une application du Store se déploie avec Intune, via le type « Microsoft Store app (new) » (basé sur winget) :

  • ciblage par groupe Entra ID (un groupe pilote, pas toute l’entreprise) ;
  • installation « disponible » dans le Portail d’entreprise ou « obligatoire » ;
  • mises à jour suivies automatiquement.

Deux précautions : vérifier l’éditeur du paquet avant de l’approuver, et tester le scénario Autopilot, encore partiellement pris en charge pour les applications du Store. La certification du Store contrôle l’absence de logiciel malveillant et le respect des règles de la boutique ; ce n’est ni un audit de sécurité ni une analyse RGPD.

Ce que Hermes Agent sait déjà faire avec Microsoft

  • Teams (conversation) : adaptateur natif Bot Framework : messages privés, conversations de groupe, canaux. À prévoir : inscription d’application Entra ID, point d’accès HTTPS public, liste d’utilisateurs autorisés.
  • Teams (validation) : les commandes sensibles arrivent sous forme de carte adaptative : approuver une fois, pour la session, toujours, ou refuser. À prévoir : refus par défaut si aucune liste d’utilisateurs n’est configurée : à garder.
  • Teams (réunions) : pipeline de réunions via Microsoft Graph : abonnements, transcriptions, résumé posté dans un canal ou une conversation. À prévoir : consentement administrateur, renouvellement régulier des abonnements Graph.
  • Microsoft Foundry : authentification sans clé via Entra ID (chaîne DefaultAzureCredential : principal de service, identité managée, Azure CLI…). À prévoir : choix du modèle et de la région d'hébergement.
  • Clouds souverains (GCC High, DoD, 21Vianet) : autorité d’authentification configurable. À prévoir : correctif proposé pour que les appels Graph suivent le bon cloud (voir plus bas).

Le point que je trouve le plus mûr : la validation des commandes dans Teams. Quand l’agent veut exécuter une commande jugée dangereuse, il envoie une carte avec quatre boutons, et seuls les utilisateurs de la liste autorisée peuvent cliquer. Sans liste, le clic est refusé. C’est exactement le comportement qu’on attend d’un outil qui a accès à un terminal.

Ce qui manque pour un usage généralisé

  • Pas d’outillage d’administration documenté : la documentation ne décrit ni console d’administration centralisée, ni SSO, ni journal d’audit.
  • Des secrets dans un fichier : les identifiants Teams et Graph sont lus depuis un fichier .env sur la machine qui héberge la passerelle.
  • Un contrôle d’accès par identifiants : l’accès au bot Teams se règle par une liste d’identifiants d’objet Entra ID, pas par un groupe.
  • Une intégration Teams exigeante : inscription d’application, consentement administrateur, URL publique stable avec certificat valide, rotation des secrets. Comptez quelques heures avec de l’expérience Azure.
  • Un agent qui agit sur le poste : il peut lancer des commandes et des scripts. Sans règles Intune ni environnement isolé (Docker, par exemple), c’est un risque d’IA non maîtrisée.

Deux correctifs que j’ai proposés

En lisant le code Microsoft de Hermes Agent, j’ai trouvé deux défauts concrets et proposé un correctif pour chacun. Les deux sont en revue chez les mainteneurs, pas encore intégrés.

1. Microsoft Graph dans les clouds souverains (PR #135618). La documentation indique comment pointer l’authentification vers login.microsoftonline.us pour GCC High, mais le client Graph envoyait toujours ses requêtes vers graph.microsoft.com. Or un jeton émis pour un cloud souverain n'est pas accepté par le service mondial : toutes les requêtes étaient rejetées. Le correctif déduit l'adresse Graph du scope configuré, en se limitant aux quatre racines Graph publiées par Microsoft. Aucun nouveau paramètre, et le jeton n'est jamais envoyé ailleurs.

2. Résumés de réunion en français (PR #135619). En mode webhook, les sections vides d’un résumé (décisions, actions, risques) affichaient « None » en anglais, alors que le mode Graph affichait déjà « Aucun ». Le correctif utilise la même traduction dans les deux modes.

Chaque correctif est accompagné d’un test qui échoue sans lui, et passe les contrôles du projet.

Ma checklist avant un pilote

  1. Périmètre : un cas d’usage, un groupe pilote Entra ID, une installation « disponible » (pas « obligatoire ») dans Intune.
  2. Modèle : Microsoft Foundry avec authentification Entra ID (pas de clé API à stocker), dans une région européenne.
  3. Teams : une inscription d’application dédiée, une liste d’utilisateurs autorisés, jamais l’accès ouvert à tout le tenant, réponse uniquement sur mention dans les canaux.
  4. Exécution : validation des commandes activée, exécution dans un environnement isolé plutôt que directement sur le poste.
  5. Secrets : fichier .env aux droits restreints, rotation planifiée des secrets Entra ID.
  6. Réunions : consentement administrateur documenté, tâche planifiée de renouvellement des abonnements Graph.
  7. Formation : les utilisateurs du pilote formés aux usages et aux limites. L’article 4 de l’AI Act, réécrit par le règlement (UE) 2026/1744 en vigueur depuis le 27 juillet 2026, demande désormais de « favoriser » la maîtrise de l’IA par le personnel (ceci n’est pas un conseil juridique).

À retenir

  • Le Microsoft Store rend Hermes Agent déployable par Intune : c’est la vraie nouveauté pour une DSI.
  • L’intégration Teams, Graph et Foundry existe déjà et elle est sérieuse, notamment la validation des commandes par carte adaptative.
  • La gouvernance (secrets, accès, audit) reste à la charge de l’entreprise : prévoir un pilote cadré avant toute généralisation.
